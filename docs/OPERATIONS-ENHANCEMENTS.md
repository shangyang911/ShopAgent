# 消息待办、商品批量管理与客户详情

## 页面入口

- `/notifications`：侧栏通知入口。汇总当前库存风险、收款满 24 小时仍待发货的订单、处理中售后。支持分类、已读/未读筛选和分页。
- `/products`：商品卡片下方多选，或全选当前页；预览后批量上架、下架、归档、收藏或取消收藏。
- `/customers`：选中客户后显示经营汇总、分页订单、客户标签和跟进备注；保留原地址管理。
- 客户详情的“为该客户创建订单”进入 `/orders?create_customer_id={id}`，重新加载客户和地址，优先选中默认地址。

## 模块划分

后端各模块按 `router.py`（HTTP、参数、鉴权）、`schemas.py`（输入契约）、`service.py`（查询与事务）、`models.py`（持久化）分工：

- `app/features/notifications/`：跨业务只读来源查询与当前账号的已读记录。
- `app/features/products/batch/`：商品批量预览、版本校验、整批提交与审计回执。
- `app/features/customers/details/`：客户经营事实、历史订单和独立跟进资料。

前端对应功能采用 `api/`、`model/`、`composables/`、`components/` 分层，视图只负责页面组合。`App.vue` 统一持有通知角标，通过 `shared/navigation/notifications.ts` 注入契约提供给侧栏，避免共享导航反向依赖业务模块。角标每分钟及窗口重新获得焦点时刷新；消息页提供手动刷新。

关键注释覆盖已读与处理状态、历史事实口径、请求先后顺序、提交重试、锁顺序和草稿保护，不逐行复述代码。

## 消息规则

- 待办读取真实当前状态；标记已读不会关闭库存风险、更新订单状态或结束售后。
- 来源键按库存告警 ID、订单 ID、售后单 ID 去重。同一来源不会重复出现；库存风险恢复后再次触发使用新的告警 ID，再次显示未读。
- 业务处理完成后不再出现在当前待办中。当前版本不提供已完成待办历史查询。
- 每个账号分别保存已读状态。已读标记重复提交不会重复插入；来源已消失时返回 409，刷新后重试。
- 仅包含有可靠付款时间的超时订单；未知历史时间不推算为超时。库存来源同时核对当前库存和监控规则，避免补偿任务执行前显示已恢复风险。
- 列表数据库分页，未读角标统计当前账号全部活动待办，不受页面筛选和页码影响。
- 页面明确显示全局待办和未读数量。“当前页标为已读”仅处理可见页；“全部标为已读”跨全部分类和分页处理当前账号待办。当前页已读但其他页仍有未读时，展示说明和“查看全部未读”入口。
- 列表成功刷新后将同一响应中的未读数同步到导航，正在途中的旧角标轮询随即失效，防止全部已读后红色角标恢复。商品页顶部提示点也仅在确有未读时显示。

## 批量事务

- 选择范围限当前页，最多 100 个商品；翻页或刷新列表清除选择。
- 预览不写数据库。确认时重新按商品 ID 顺序加锁，核对预览摘要。任一商品删除、改名或待修改状态变化都会拒绝整批提交，需重新预览。
- 状态变更复用库存告警评估，不修改库存、价格、订单预留和 SKU 数量；下架不取消已有订单。
- 收藏操作仅影响当前账号。成功后刷新商品与收藏状态。
- 同一账号先锁账号再锁商品，幂等回执和全部变更同事务提交；网络重试沿用同一提交键。相同提交键对应不同内容返回 409。
- `product_batch_logs` 保存操作者、变更前后快照和提交摘要。当前范围不包含价格批改、商品删除和表格导入。

## 客户事实与资料

- 订单数包含该客户全部订单；确认收款订单数只读取真实确认收款记录。
- 收款和实际退款分开聚合，避免连接多个订单行和多笔退款导致金额重复。净确认收款不是利润，也不代表已与支付机构对账。
- 最近购买以最近确认收款时间展示。订单创建时间只使用已核实业务事实，无可靠来源则显示待核实。
- 常购商品按已收款订单中的历史商品名称汇总购买件数，未扣退件；不按商品当前名称重写历史。
- 跟进资料独立存储，最多 20 个去重标签，每个 30 字，备注最多 5000 字；版本号防止覆盖其他窗口的修改。
- 订单翻页不覆盖未保存备注。保存冲突后保留草稿；用户明确重新加载才放弃草稿并读取新版本。切换客户或卸载后丢弃旧请求响应。

## 接口

```text
GET  /api/notifications
POST /api/notifications/read
POST /api/notifications/read-all
POST /api/products/batch/preview
POST /api/products/batch/apply
GET  /api/customers/{id}
PUT  /api/customers/{id}/profile
```

全部接口要求管理员登录。后端正常启动时创建 `notification_reads`、`product_batch_logs`、`customer_profiles` 三张新增表，保留已有业务表和数据。

## 验证

```powershell
# backend/
.venv\Scripts\python.exe -m unittest discover -s tests -q

# frontend/
npm test
npm run build
npm run check:architecture
```

新增隔离回归覆盖账号已读隔离、风险恢复与再次触发、待办分页、批量预览只读、版本冲突、提交失败回滚、幂等重试、批量收藏、客户收款退款去重、标签校验与版本冲突，以及前端旧请求和草稿保护。

最近验收：后端共 181 项，167 项通过、14 项可选 MySQL 测试跳过；前端 140 项通过，生产构建、架构检查、全量源码格式检查通过。通知来源查询额外验证可编译为 MySQL SQL，但未运行真实 MySQL 并发验收。

浏览器使用独立 SQLite 和 8002/5175 端口，完成消息未读角标、标记已读仍保留待办、两件商品预览后批量下架、客户经营汇总、标签备注持久化、带入客户及默认地址创建订单；消息页和客户详情同时检查 390px 手机布局，修复客户历史订单表撑宽内容的问题。测试数据只写入 `.local-test/operational-features-smoke.db`。

消息页交互修复另验证：超过一页的消息仅标记当前页后，全局仍保留其他页未读；跨全部分类和分页标记后角标归零，已读待办保留；新风险出现后恢复未读提示。增加旧角标轮询不得覆盖最新列表统计、全部已读失败保留原统计、离页后不发起旧操作刷新等回归。筛选框统一为 42px 高度、圆角、独立标签和箭头，并检查手机宽度无横向溢出。
