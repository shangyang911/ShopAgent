# 单店管理平台：售后、库存纠错与包裹物流

本轮围绕现有单店、单仓、管理员录单和人工确认收款流程补齐闭环。订单导入、员工权限、多规格 SKU 仍按真实业务需要另行设计；本轮没有引入多仓、支付网关或成本利润核算。

## 页面入口

- 商品管理：经营状态改为草稿、上架、下架、归档；库存风险独立显示，读取库存中心的默认阈值、商品阈值与监控开关。评分、评论数不再作为人工编辑和目录筛选入口。颜色和配送说明可不填，金额展示使用人民币。
- 订单详情：新增“售后与退款”，支持仅退款、退货退款、实际退款凭据登记及退件验收。
- 库存中心：新增“盘点、报损与入库更正”，展开后创建草稿、核对冻结的差异预览，再确认入账。
- 发货工作台：按包裹切换物流记录，显示部分或全部包裹的平台签收情况；地图默认折叠。
- 经营概览：显示本期已登记实际退款及净确认收款；净确认收款不等于利润。
- 运营助手：沿用管理员身份，协助查单、查库存和物流；多包裹物流进入工具结果。模型没有执行退款或验收入库的权限。

## 售后规则

1. 售后、退款和退件验收分别保存，不能用一个订单状态替代这些事实。原有历史 `refunded` 状态仍能读取，新 HTTP 状态操作不能直接标记退款。
2. 同单最多一个处理中售后。申请金额不得超过已核实收款减累计实际退款；没有可靠收款事实的历史订单不能按应收额假定已付款。
3. 每次实际退款记录金额、带时区的发生时间、凭据和操作者。发生时间不能早于已确认收款，也不能在未来。后台登记不调用支付机构。
4. 未出库订单全额退款时，在同一事务中取消履约并释放预留；在途或已完成订单保留原履约状态。部分退款不会把整单标记为退款终态。
5. 未结售后暂停交接出库；撤销仅允许尚无退款和验收事实的申请。
6. 退货数量按原订单商品行核对，累计数量不能超过购买数量。验收时逐项填写合格和损坏件数，两者之和等于本次申请退件数量；本轮一次完成整张退货单验收，不支持分批收件。
7. 合格件通过库存流水恢复可售数量；损坏件只登记事实。仅发生退款、物流退回或人工关闭异常均不会恢复库存。
8. 退款记录使用提交键保护重试；验收记录一旦确认只读。售后事件、退款事实与相关库存动作统一提交，失败整体回滚。

订单工作台的“已退款”视图按实际退款记录查询，包含部分退款、全额退款以及历史已标记退款的订单；订单仍可同时属于“已完成”或“配送中”履约视图。仅创建申请、尚未登记实际退款的售后进入“售后处理中”。数量、分页、多选和 CSV 导出共用同一筛选逻辑，退款多次也不重复计单。售后操作后自动刷新当前列表与计数。

## 跨页面一致性补充

- 发货工作台按完整包裹清单汇总签收，未知或未同步包裹也计入总包裹数。历史已标记退款且已经实际交接的订单仍按履约事实进入已发货或已完成视图，未出库退款不进入队列。
- 售后处理中订单在发货页明确暂停交接，单笔按钮及批量预览均校验；批量预览重新读取最新售后状态，避免只信任选单时的旧数据。
- 订单的关联库存流水及对应导出包含退件验收入库，按售后单关联回原订单，不遗漏这类来源凭据。
- 下单选择器使用可售状态白名单，下架和归档商品有库存也不允许选择。商品列表支持过期响应保护、稳定排序和总页数缩小时自动回退。
- 运费筛选修改后，导出先更新相同条件的预览；查询失败时保留旧结果并阻止导出，避免预览与文件使用不同条件。
- 客户列表忽略较慢的旧响应；运营助手查询支持售后处理中视图，同时返回实际退款金额和原履约状态。

## 库存纠错规则

- 盘点填写实物在库数量，包含有效预留。调整后可售 = 实盘在库 − 有效预留，不能为负。
- 报损填写负数差额，只扣可售，不挪用已经分配给订单的预留数量。
- 入库更正必须关联原已确认入库单，商品必须属于原单；差额另记流水，原单数量和原始流水保持只读。
- 创建草稿不改库存。草稿冻结可售、预留、最新流水版本，确认时按商品 ID 顺序加锁，并使用数据库当前读核对版本。发生任何相关库存流水变化，都应作废旧草稿并重新核对。
- 多商品整单确认，任一商品失败则整单不入账；重复确认不会重复记账。已确认单据不能删除或作废。

## 包裹物流规则

一号包裹保留原轨迹表与接口，附加包裹增加独立表。共同使用 `tracking/service.py` 的领取任务、外部查询、核对版本后落库算法；单号、节点去重、错误、查询间隔和占用令牌均按包裹隔离。

附加包裹异常进入现有异常跟进面板，并标明包裹号。主包裹签收不会停止其他包裹的后台轮询，也不会解除其他包裹的异常。整单“全部包裹显示签收”仍不自动修改人工订单完成状态。

## 模块与接口

后端新增 `features/aftersales/`，分为模型、输入契约、只读查询、事务服务和 HTTP 路由；库存纠错位于 `features/inventory/`，复用 `operations/inventory.py` 的流水规则。包裹物流扩展放在已有 `shipping/tracking/` 下，通过 `context.py` 适配主包裹和附加包裹，避免复制同步算法。

前端新增 `features/aftersales/{api,model,components}`，库存调整也分别存放 API、模型、组件。页面仅挂载面板，公共布局样式在 `styles/business-panels.css`。代码注释说明状态边界、锁顺序、事务、幂等、过期响应和输入转换规则。

主要新增接口：

```text
GET/POST /api/orders/{id}/aftersales
POST     /api/orders/{id}/aftersales/{case_id}/refunds
POST     /api/orders/{id}/aftersales/{case_id}/inspection
POST     /api/orders/{id}/aftersales/{case_id}/cancel
GET/POST /api/inventory/adjustments
POST     /api/inventory/adjustments/{id}/confirm
POST     /api/inventory/adjustments/{id}/cancel
GET      /api/shipping/orders/{id}/tracking-packages
GET      /api/shipping/orders/{id}/packages/{no}/tracking
POST     /api/shipping/orders/{id}/packages/{no}/tracking/sync
```

所有新增业务接口继承管理员登录态。

## 启动与兼容

新增模型已在数据库入口注册，正常重启后端时创建缺失表。采用新增表方式，不删除或重建原订单、商品、库存和物流表，不猜测历史退款金额，不覆盖历史评价。

旧商品 `Low stock`、`Out of stock` 在响应中归为上架状态，并继续参与上架查询和下单；新编辑保存规范经营状态。库存标签独立按实际数量和阈值计算，避免旧标签与库存矛盾。
