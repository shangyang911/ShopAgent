# 三个核心模块 PRD 大纲（V1.0 建议稿）

适用项目：现有 Vue 3 + FastAPI 单店电商后台。

本文件是可供产品、设计、研发和测试评审的需求大纲。业务规则、阈值和验收目标均为建议值，需要在实施前由业务负责人确认；本文不代表这些能力已经实现。

## 0. 目标、范围与共用口径

### 0.1 本轮目标

- 经营概览：让负责人快速知道经营结果和待处理事项，并能从数字进入业务明细。
- 库存中心：解释每次数量变化，提供有凭据的补货入库和有效的低库存提醒。
- 订单工作台：缩短查单、核对、打印配货资料的操作路径，保留完整操作依据。

### 0.2 范围边界

- 单店、单仓、人民币；一个现有商品记录作为最小库存管理单元，单位暂统一为“件”。多规格 SKU、散装计量另期设计。
- 复用现有手工“确认收款”动作；本轮补齐收款事实和时间记录，不接支付网关，不做账期赊销、分期或部分收款。
- 补货单支持人工录入、确认入库；不扩展供应商、采购合同、采购审批和多仓调拨。
- 订单保留现有状态链；本轮不增加完整售后、部分退款、退货验收、部分发货或骑手调度模块。
- 允许业务角色由同一个管理员兼任。本轮记录实际登录账号，不以“老板／仓管”等业务角色替代真实操作者；完整账号及权限管理另期建设。
- 现有已退款订单缺少退款金额和发生时间时，不据状态猜测退款事实。退款分析指标在补齐可靠记录后启用。

### 0.3 业务角色与能力边界

- 经营负责人／店长：查看经营概览和明细；确认收款、取消订单；核对补货和告警规则。
- 仓管／库管：查看库存与流水；录入并确认补货；设置商品库存阈值；查看关联订单。
- 订单运营／客服：查单、核对订单、追加内部备注、查看时间线和打印记录。
- 打单配货员：筛选待发货订单、查看商品和收件快照、打印和补打配货单。
- 若后续拆分员工权限，以上写操作由服务端校验；不能只隐藏按钮。现阶段所有授权动作继承现有管理员权限。

### 0.4 数据共识

- 金额统一使用 Decimal，人民币保留两位小数；界面展示元，禁止使用浮点运算累计金额。
- 时间存储统一为 UTC，页面按 `Asia/Shanghai` 展示和划分自然日；历史无时区时间必须先核实原含义后迁移。
- 时间查询采用左闭右开区间 `[start_at, end_at)`；选择某日截止时，转换为次日 00:00 的排他上界。
- 业务写入采用服务端生成的发生时间；补录历史业务必须保留原业务时间、补录时间和补录人，并标记补录来源。
- 成功的订单状态、库存变化、收款记录及相关业务事件必须在同一事务中提交；失败时整体回滚。
- 重复请求通过唯一业务键／幂等键识别，禁止重复收款、重复入库、重复释放库存。
- 现有 `products.stock` 已在创建订单时扣减，因此本期映射为 `available_quantity`（可售数量）。

## 1. 经营概览

### 1.1 核心用户与用户故事

- 经营负责人：作为负责人，我希望打开首页就能看到本日已确认收款、订单量和变化趋势，以决定是否需要调整经营动作。
- 店长：作为店长，我希望直接进入待发货、超时未发货和低库存列表，以优先处理影响履约的问题。
- 运营：作为运营，我希望按同一日期范围查看指标、趋势和订单明细，以解释数据变化。

### 1.2 功能点清单

- P0：日期选择，提供今日、昨日、近 7 天、近 30 天、自定义；默认今日。
- P0：关键指标卡，展示确认收款额、确认收款订单数、新建订单数、完成订单数、平均确认收款订单金额。
- P0：趋势区，金额和单量分别展示；支持日粒度，超过 90 天可切周／月粒度；点击数据点进入对应明细。
- P0：实时待办，展示待发货、超时未发货、低库存、缺货；每个入口附数量。
- P0：指标说明和数据更新时间；指标卡可进入带同口径条件的明细列表。
- P0：加载、空数据、刷新失败的独立状态；失败保留上一份成功数据并提示更新时间。
- P1：热销商品排行，按确认收款订单对应的商品数量／商品金额排序，运费不分摊进商品销售额。
- P1：退款金额、净确认收款；仅在具备结构化退款事实后启用。
- 暂缓：利润、毛利率、支付转化率、流量来源；当前缺少历史成本、支付和访问数据，不推算这些指标。

### 1.3 关键字段及注释

- `period_start`、`period_end`：统计时间边界，明确所使用的业务时区。
- `as_of`：统一计算截至时点；同屏指标、趋势和下钻条件共用。
- `currency`：本期固定 `CNY`。
- `confirmed_receipt_amount`：区间内有效确认收款记录的金额合计，包含运费，文案明确为“已确认收款（含运费）”。
- `confirmed_receipt_order_count`：区间内首次成功确认收款的去重订单数。
- `created_order_count`：按订单创建时间统计的新建订单数。
- `completed_order_count`：按首次完成时间统计的完成订单数。
- `average_confirmed_order_amount`：确认收款额除以确认收款订单数；本期每单一次全额确认。
- `comparison_value`、`change_rate`：同口径对比值、变化率。
- `todo_pending_shipment_count`：截至 `as_of` 当前仍待发货的订单数。
- `todo_overdue_shipment_count`：当前待发货且等待时长达到阈值的订单数。
- `low_stock_product_count`：当前触发低库存或缺货的去重商品数；分级展示时两类不重复计数。
- `data_coverage_start`：完整事件数据开始覆盖的时间；历史缺失时在页面说明。

### 1.4 核心指标业务规则

1. 确认收款额 = `SUM(receipt.amount)`，过滤确认时间在所选区间且收款事实有效的记录。手工确认只代表后台已登记确认，页面不能宣称已与银行／支付机构对账。
2. 确认收款订单数按订单去重；重复点击、超时重试均不得重复入账。金额由服务端读取订单应收快照，不能信任前端传入值。
3. 新建订单数包含在区间内创建、随后取消的订单；它反映录单规模。取消率若后续增加，必须单独定义分母和观察窗口。
4. 完成订单数按 `completed_at` 统计，不能用当前状态结合 `updated_at` 推导完成日期。
5. 平均确认收款订单金额 = 确认收款额 / 确认收款订单数；分母为 0 时显示 `—` 并说明“本期无确认收款订单”。
6. 取消和退款不会删除曾发生的收款记录。退款指标启用后，退款计入退款实际登记发生日；净确认收款 = 同一区间确认收款额 - 已确认退款金额，不追溯覆盖原收款日。
7. 订单总额的存量求和不作为每日确认收款额；当前处于已付款状态的订单集合也不能代表历史付款发生量。
8. 今日对比昨日同一时刻；完整日期区间对比前一个等长区间；未结束周期对齐前周期相同已过时长。
9. 对比基数为 0：本期为 0 显示“持平”；本期大于 0 显示“新增”，不显示无穷大百分比。其余变化率 = `(本期 - 对比期) / 对比期 × 100%`。
10. 趋势缺少业务发生的日期补 0；因数据源缺失而不可计算的日期显示“无可靠数据”，不能补 0。
11. 金额和单量使用独立图表或明确的独立坐标轴，避免元与单混用同一刻度。

示例：昨天创建、今天 10:00 确认收款 520 元的订单，计入昨天的新建订单数、今天的确认收款额和确认收款订单数；明天取消该订单，今天的历史收款事实仍保留。若明天登记退款，退款归明天。

### 1.5 待办与刷新规则

- 待办按当前状态统计，不跟随顶部历史日期筛选；区域标题明确标注“当前待办”。
- 默认“超时未发货”为确认收款后满 24 个自然小时、仍处于待发货状态；本期不引入营业日历。
- 无可靠付款时间的历史订单单独标为“付款时间待核实”，不计算虚构的超时时长。
- 点击卡片时传递指标对应的时间字段、区间、截至时点和状态条件。例如收款额下钻传付款时间条件，而非创建时间条件。
- 建议数据缓存最长 60 秒，手动刷新可获取新快照；显示更新时间。页面隐藏时暂停轮询，避免后台重复请求。
- 待办跳转保留状态、超时规则等条件；不叠加首页所选历史日期，避免遗漏当前待处理订单。

### 1.6 验收要点

- 三个订单分别在不同日期创建、付款、完成，能够按对应业务时间准确归入指标。
- 同一确认收款请求提交两次，只增加一次金额和一次订单数。
- 指标卡、趋势和下钻明细在相同 `as_of` 下可核对；金额加总结果一致。
- 基数为 0、无订单、历史时间缺失、接口失败均有明确展示，不混淆“0”和“未知”。

## 2. 库存中心

### 2.1 核心用户与用户故事

- 仓管：作为仓管，我希望查到商品当前可售、已预留和账面在库数量，并解释最近每笔变化。
- 仓管：作为仓管，我希望一次录入多个商品的实际到货数量，并在确认时统一入账，以避免漏入库和重复入库。
- 店长：作为店长，我希望在商品即将缺货时收到明确提醒，补足后提醒能自动消失。
- 订单运营：作为运营，我希望从库存扣减追溯到订单，以快速判断库存被哪些订单占用。

### 2.2 功能点清单

- P0：库存总览，支持商品名称／编码、分类、库存等级筛选，展示可售、预留、账面在库和预警阈值。
- P0：库存流水，支持商品、类型、时间、关联单号、操作者筛选及订单／补货单跳转。
- P0：补货入库，支持多商品草稿、校验、确认、详情查看；已确认单据只读。
- P0：低库存提醒列表，支持缺货／低库存筛选、查看、确认已读、进入补货入口。
- P0：单商品监控开关、阈值覆盖和默认阈值；阈值修改保留记录。
- P0：订单创建、取消、开始配送、相关库存释放自动产生日志，不允许绕过库存流水改数量。
- P1：流水及入库单 CSV 导出；盘点、报损和入库更正另期设计受控调整流程。
- 暂缓：采购、供应商、成本核算、多仓、批次保质期、自动补货和完整盘点模块。

### 2.3 库存数量定义与联动规则

- `available_quantity`：可售数量，映射现有 `products.stock`。
- `reserved_quantity`：有效、尚未出库的订单预留数量，建议按预留记录汇总。
- `on_hand_quantity`：账面在库数量，满足 `可售 + 预留 = 账面在库`。它是系统账面值，实物准确性需要实际盘点确认。
- 创建订单 Q 件：可售 `-Q`、预留 `+Q`、账面在库不变；校验可售不少于 Q。
- 确认收款：三类数量不变；不再次扣减。
- 未出库订单取消：可售 `+Q`、预留 `-Q`、账面在库不变；每份预留只能释放一次。
- 开始配送：作为本期实物出库节点，预留 `-Q`、账面在库 `-Q`，可售不再扣减。
- 配送完成：数量不变。
- 补货确认 Q 件：可售 `+Q`、账面在库 `+Q`，预留不变。
- 未出库订单若通过已有退款能力终止，按预留是否仍有效释放一次；已出库订单仅发生退款时不自动增加库存，实物退货需后续验收流程。
- 打印和补打配货单均不改变库存或订单状态。
- 三类数量均不得为负，商品锁定顺序一致；库存余额、流水、预留状态和订单事件一次事务提交。

示例：初始可售 20、预留 0、账面在库 20；下单 3 件后为 17／3／20；开始配送后为 17／0／17；补货 10 件后为 27／0／27。

### 2.4 库存流水字段及注释

- `movement_id`：不可重复的流水标识；流水只追加、不直接修改或删除。
- `product_id`、`product_name_snapshot`：关联商品及发生时名称；一期商品编码可使用现有商品 ID，无须同时引入完整 SKU 系统。
- `movement_type`：期初结转、补货入库、订单预留、预留释放、配送出库。
- `available_before`、`available_delta`、`available_after`：变更前、变化值、变更后可售数量，变化值带正负号。
- `reserved_delta`、`on_hand_delta`：同次业务对预留和账面在库的影响。
- `reference_type`、`reference_id`、`reference_number`：来源类型、来源 ID、业务单号，用于双向追溯。
- `reason`：补货说明、取消原因或系统变更原因。
- `actor_id`、`actor_name_snapshot`：实际操作者及当时姓名；系统动作标记为系统。
- `occurred_at`：服务端业务发生时间；与相同事务的订单事件保持关联。
- `idempotency_key`：同一业务动作的唯一键，防止重试造成重复入账。

### 2.5 补货入库字段及规则

- 单头：`receipt_id`／`receipt_number`（唯一入库单号）、`status`（草稿／已确认／已作废）、`remark`、`created_by`、`created_at`、`confirmed_by`、`confirmed_at`。
- 明细：`line_id`、`product_id`、`product_name_snapshot`、`quantity`；数量必须为正整数；同单重复商品合并或明确阻止重复行，本期建议自动合并。
- 草稿可修改、删除；草稿作废不影响库存。已确认单据不能改数量、删除或再次确认；需要纠错时保留原单并走受控更正，不做无日志回写。
- 建议每单最多 100 个不同商品；所有明细校验通过后一次提交，任意一行失败则整单不入库。
- 点击确认前展示商品种数、总件数和明细；确认按钮防重复，服务端仍必须幂等。
- 本期不要求采购价格；不以缺失价格或 0 成本计算库存价值和利润。

### 2.6 低库存提醒字段及注释

- `monitor_enabled`：是否监控该商品，默认对在售商品启用。
- `threshold_override`：商品专属阈值；`null` 继承默认值，`0` 是有效阈值，不能当作未设置。
- `effective_threshold`：最终生效阈值，建议全局默认 5 件。
- `severity`：低库存／缺货；等级由可售数量计算，不使用人工填写的商品状态标签推导。
- `alert_id`：本次告警事件标识。
- `alert_status`：处理中／已恢复／已关闭。
- `first_triggered_at`、`last_evaluated_at`、`resolved_at`：首次触发、最近评估、恢复时间。
- `acknowledged_at`、`acknowledged_by`：已读信息；已读不代表库存问题已解决。
- `available_at_trigger`、`current_available`：触发时和当前可售数量，支持解释告警变化。
- `close_reason`：已恢复、关闭监控、商品归档等结束原因。

### 2.7 低库存提醒业务规则

1. 监控范围：启用监控的在售商品；草稿、归档商品默认不参与，已有“缺货”标签商品仍需监控。
2. 缺货：可售数量 = 0；低库存：`0 < 可售数量 <= 生效阈值`；正常：可售数量 > 阈值。缺货是更高等级，两个等级互斥。
3. 恢复条件：可售数量严格大于阈值。阈值为 5 时，从 0 补到 5 仍属于低库存，补到 6 才恢复。
4. 每次库存事务成功、阈值修改、监控开关或商品可售状态变化后重新评估；另建议每 5 分钟做一次补偿校验。
5. 同一商品同时最多一个未结束告警；例如库存 4→3→0，更新同一告警并升级为缺货，不产生三个告警。
6. 低库存列表覆盖缺货；分级统计时“低库存”和“缺货”互斥，合计按商品去重。
7. 补货、取消订单释放预留等导致恢复时自动结束告警；恢复后再次跌破阈值，创建新的告警事件。
8. 调整阈值同样可能触发或恢复告警；关闭监控时标记关闭原因，不伪装为“补货恢复”。
9. 已读仅改变阅读状态；不隐藏库存风险，不影响老板概览的风险商品数。
10. 提醒入口携带商品进入补货草稿，数量由用户填写；不默认自动采购。
11. 本期通知渠道仅站内列表和待办入口，外部短信、邮件、自动采购不纳入范围。

### 2.8 验收要点

- 在阈值为 5 的情况下，库存 6→5 触发低库存，5→0 升级缺货，0→5 仍低库存，5→6 恢复。
- 默认阈值 5、专属阈值 0 两种情况分别正确；关闭和重新启用监控符合告警生命周期。
- 同一入库单重复确认，库存和流水均只增加一次；两名用户同时提交不丢失数量。
- 下单、取消、配送、补货可以按来源单据核对流水；打印动作不生成数量变化。
- 已有预留的商品禁止物理删除；无活动预留的历史商品即使删除，旧流水和单据快照仍可识别。

## 3. 订单工作台

### 3.1 核心用户与用户故事

- 打单配货员：作为配货员，我希望快速筛选尚未处理的待发货订单，批量取得清晰配货单，以减少切换和漏配。
- 客服：作为客服，我希望通过订单号、电话或收件人定位订单，并查看发生过的操作，以准确答复客户。
- 店长：作为店长，我希望知道订单何时收款、由谁取消、是否多次请求打印，以定位履约问题。

### 3.2 功能点清单

- P0：列表与快捷标签，保留分页，提供全部、待付款、待发货、配送中、已完成等入口。
- P0：关键词搜索，覆盖订单号、完整收件电话、收件人、商品名称快照；支持组合筛选。
- P0：高级筛选，支持创建／付款／完成时间、订单状态、金额区间、是否请求过打印。
- P0：订单详情，集中展示客户、收件快照、商品快照、金额、内部备注、操作时间线和关联库存流水。
- P0：现有业务动作，确认收款、取消、开始配送、完成配送；统一写入时间线和对应时间字段。
- P0：追加内部备注，保留作者、时间及原内容；修改通过更正／追加记录说明。
- P0：单单和批量配货单打印、历史文档查看、补打；不自动改变订单状态。
- P0：打印请求记录筛选和风险提示；“从未请求打印”不得文案化为“确定未出纸”。
- P1：常用筛选保存、CSV 导出、合并拣货汇总单和快捷键。
- 暂缓：跨页全量选择、批量确认收款／取消／发货、称重和扫码复核；避免把打印优化扩大为完整仓储系统。

### 3.3 搜索筛选字段及注释

- `keyword`：统一关键词，去首尾空格；订单号优先精确匹配，完整电话精确匹配，收件人和商品快照名称模糊匹配。
- `statuses[]`：支持多选订单状态；组内为 OR，与其他筛选项为 AND。
- `time_field`：`created_at`／`paid_at`／`completed_at`，默认创建时间，界面明确当前所用口径。
- `start_at`、`end_at`：所选业务时间范围；无可靠时间的历史记录不伪造匹配，提供“时间待核实”入口。
- `min_total`、`max_total`：订单应收总额区间，包含运费，均含边界；下限不得大于上限。
- `print_request_status`：从未请求／已请求；可另筛“多次请求”。
- `page`、`page_size`、`sort`：默认每页 20 条，可选 50 条；默认创建时间倒序，同时间按订单 ID 倒序稳定排序。
- `selected_order_ids`：当前页勾选的订单，最多 50 单；更换筛选或翻页后清空并明确提示。
- `as_of`：从概览下钻时携带的快照边界，便于与概览数值核对。

### 3.4 搜索筛选规则

- 默认可选最近 30 天，并以可见筛选条件呈现；用户可清除日期查历史，不通过隐藏默认值漏掉旧单。
- 商品名称搜索使用下单时快照，商品后来改名不影响历史订单检索。
- 金额和时间范围校验失败时指出具体字段；空结果展示当前条件和清空入口。
- 状态标签数量按其他已选条件计算，暂不施加标签本身的状态条件，使切换后的数量有解释性。
- 筛选和分页写入 URL；从详情返回保留条件和位置；新标签页打开、前进后退行为正常。
- 请求采用取消或请求序号控制，较早响应不得覆盖最新筛选结果。
- 从概览进入后显示对应的“付款时间”等筛选标签，用户可主动改回创建时间。

### 3.5 订单操作时间线字段及注释

- `event_id`：唯一事件 ID。
- `order_id`：关联订单 ID；不依赖可变的展示名称。
- `sequence`：订单内单调递增序号，解决同一秒多个动作的排序问题。
- `event_type`：创建订单、确认收款、取消订单、开始配送、配送完成、备注追加、打印请求、补打请求、更正记录、历史数据接入等。
- `occurred_at`：业务发生时间，展示到秒；需要更精确排序时使用 `sequence`。
- `recorded_at`：系统记录时间；历史补录时与业务时间区分。
- `actor_type`、`actor_id`、`actor_name_snapshot`：用户／系统／迁移来源、实际账号和当时显示名。
- `from_status`、`to_status`：发生状态变化时记录前后值；非状态事件为空。
- `summary`、`reason`：操作摘要和业务原因；取消、补打、更正等要求填写原因。
- `changed_fields`：结构化的变化字段及前后值；前台按权限展示必要信息。
- `related_receipt_id`、`related_movement_ids`、`print_job_id`：关联收款、库存、打印记录。
- `request_id`／`correlation_id`：把同一业务动作的多类记录串起来。
- `idempotency_key`：重试去重键；重复提交不重复展示成功事件。

### 3.6 时间线业务规则

1. 所有入口统一留痕：订单页、配送页、接口和系统任务触发同一业务动作时，必须调用同一事件记录规则。
2. 只在业务事务成功后出现成功事件；状态修改、库存流水和事件一起提交。失败不会留下“已发货”等成功痕迹。
3. 同一动作产生的收款、状态、库存信息合并为一个可展开的业务节点，保留关联记录，避免时间线被重复文案淹没。
4. 默认最新在上，按订单内序号稳定排序；列表分页加载，示例每次 20 条。
5. 创建、确认收款、开始配送、完成配送同步写入对应时间字段；日后修改备注不能覆盖这些业务时间。
6. 时间线只追加、不编辑、不删除；纠错增加一条更正记录并引用原事件。操作者改名后历史记录仍显示当时姓名。
7. 内部备注只对后台可见，不自动发送给客户。
8. 当前商品、地址簿被修改或删除后，订单及其单据仍展示下单时快照。
9. 打印动作显示“请求打印”或“请求补打”，不显示未经确认的“打印成功”或“已配货”。
10. 历史付款、发货时间不能由 `updated_at` 反推；迁移时增加“历史数据接入”事件，未知发生时间明确标记未知，保留接入时间。

示例：订单创建（预留 3 件）→店长确认收款 520 元→配货员请求打印→配货员追加备注→开始配送（释放预留并出库）→完成配送。每一步均能查看操作者、发生时间和关联凭据。

### 3.7 配货单打印字段及注释

- `print_job_id`：一次批量打印请求的 ID，关联多张订单文档。
- `order_number`、`created_at`、`paid_at`：订单识别信息；历史时间未知时按未知展示。
- `recipient_name`、`recipient_phone`、`shipping_address_snapshot`：下单时收件信息，不临时读取客户地址簿替换。
- `items[]`：商品编码／ID、商品名称快照、订购数量、单位和配货勾选框；一期无规格数据时不虚构规格。
- `distinct_product_count`、`total_quantity`：商品种数、总件数，便于核对。
- `internal_picking_note`：明确供仓内使用的配货备注；避免把所有内部讨论自动印出。
- `document_revision`、`document_hash`：文档快照版本及摘要，标识补打内容是否与原版一致。
- `print_attempt_no`、`requested_by`、`requested_at`、`reprint_reason`：第几次请求、请求人、请求时间、补打原因。
- `include_amount`：是否含金额，建议默认不展示，满足仓内配货用途。

### 3.8 配货单打印业务规则

- 首次配货打印仅限当前待发货订单；开始配送、已完成订单可查看并补打已有文档，但必须带当前状态和补打标识，避免当作新任务。
- 已取消、已退款订单阻止新配货打印；已打开的旧文档在发起新打印请求前重新校验状态，提示失效。
- 本期批量选择限当前页，最多 50 单；后端重新校验权限、存在性和状态。
- 建议任一订单不符合条件时阻止本次整批生成，并列出冲突订单；保留选择供用户移除后重试，避免静默遗漏。
- A4 模板，每单从新页开始；长订单可跨页，重复订单号和表头，商品名称换行，显示本单页码和页数；预留配货／复核签字区。
- 打印内容生成时固化为文档快照；之后更改备注不会悄悄改写已生成文档。打印最新版本和补打旧版本需要明确区分。
- 每次明确的打印意图生成请求记录；接口重试复用幂等键，用户主动补打使用新请求并填写原因。
- 浏览器无法可靠确认纸张是否出纸；打印对话框被取消、打印机无纸等情况下，不能写“物理打印成功”。
- 打印不触发收款、发货或库存扣减；实际配货、出库动作仍按业务流程处理。

### 3.9 验收要点

- 组合搜索、多状态筛选、时间字段切换、金额边界、超过 100 条订单的分页均正确。
- 快速切换筛选不会出现旧请求覆盖；返回列表保留条件和页码。
- 从不同页面改变订单状态，只生成一次对应业务事件，并能关联库存变化。
- 打印对话框取消后只显示请求记录，订单状态、库存和发货时间不变。
- 50 单批量打印正常分页；某单状态已被其他人修改时明确阻止并列出冲突。
- 一单 60 行商品、多页长地址和长名称打印不丢行、不覆盖；商品改名不改变旧单据快照。

## 4. 本期所需的数据基础与迁移

### 4.1 新增或补齐的数据对象

- 订单：`paid_at`、`dispatch_started_at`、`completed_at`、`cancelled_at`，以及最近打印请求信息；时间来自业务动作，不用更新日期替代。
- 收款确认记录：订单 ID、金额、来源、确认时间、确认人、幂等键；由现有确认收款动作产生。本期只支持一次全额确认。
- 库存预留记录：关联订单行、商品、数量、状态（有效／已释放／已出库）、发生及终止时间，用于保证同一预留仅结束一次。
- 库存流水：数量变化、前后值、关联凭据、操作者与发生时间。
- 入库单及明细：草稿、确认状态和实际入库数量。
- 告警规则与告警事件：商品阈值、监控状态、等级、生命周期和已读信息。
- 订单事件：不可变业务时间线。
- 打印任务及文档：请求状态、文档快照、版本及补打记录。

### 4.2 迁移原则

- 保留当前 `products.stock` 作为可售数量；根据有效未出库订单核实预留，建立期初结转。不要把现有库存再扣一次。
- 迁移前核对可售、未出库订单和历史取消／退款异常；不根据“已退款”三个字推断商品已回仓。
- 当前在售库存编辑入口转为只读数量展示或跳转入库；未来更正也必须走有凭据的变更流程。
- 新商品的初始库存走期初入账事件；不允许新增页面悄悄生成无流水余额。
- 有可靠来源的历史收款／完成时间可补录并标注来源；无来源保留未知，并显示统计覆盖起点。
- 历史事件明细不凭空重建，使用期初／历史接入记录说明边界。

## 5. 跨模块验收、性能与实施顺序

### 5.1 跨模块一致性验收

1. 创建订单预留库存后，订单详情、库存余额和流水一致；达到阈值时，告警与概览待办同步变化。
2. 确认收款只发生一次，概览金额与订单时间线、收款明细一致。
3. 取消未出库订单后，可售恢复、预留释放、流水和时间线各出现一次；相关低库存告警按新余额重新评估。
4. 确认入库后，余额、流水、入库单状态和告警恢复在同一业务结果下可核对。
5. 开始配送消耗预留并出库，完成配送不再次扣减；任何打印都不改变数量。
6. 业务失败或事务回滚时，不得出现半张入库单、无余额变化的成功流水或虚假成功时间线。

### 5.2 可用性与性能建议

- 列表、明细和时间线均服务端分页；查询、数量汇总和导出不依赖前端把全量数据加载完。
- 建议首屏接口 P95 不超过 2 秒、单次确认操作 P95 不超过 3 秒；评审时约定数据规模、并发量及测试环境后作为正式门槛。
- 概览缓存上限 60 秒；低库存事件在业务提交后及时评估，定时校验作为补偿。
- 写入和状态切换必须覆盖并发、重试和提交失败场景；禁用按钮不能代替服务端约束。
- 刷新保留可用旧数据并显示更新时间；失败可重试，错误说明具体到字段或冲突订单。

### 5.3 建议实施顺序

1. 先统一订单时间、收款确认、预留与库存流水、事件幂等和历史数据边界。
2. 上线库存总览、入库及低库存规则；同时把现有订单动作接入流水和时间线。
3. 上线订单搜索筛选、时间线展示和配货打印。
4. 基于已经可靠的业务事实上线经营指标、趋势和待办下钻。

三个模块可以在界面上并行设计，但经营数据的验收依赖前面的业务事实和统计口径。
