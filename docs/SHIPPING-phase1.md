# 发货与物流一期（2026-10-29）

一期适用于单店、单仓、每单一个包裹的人工快递发货。原高德 Key、代理、地图组件和路线接口继续使用，页面保留地图及“高德路线”入口。地图是位置核对与驾车路线参考，不充当快递轨迹或送达承诺；它的加载、定位或路线错误不阻止快递发货。

## 操作流程

1. 订单确认收款后，在 `/shipping` 的待发货标签中查询订单，也可从订单详情直接进入该单。
2. 核对商品数量和收件快照；“订单 / 配货单”可返回订单详情和现有打印入口。
3. 选择或填写快递公司，录入/扫描运单号，保存快递信息。此时不改变订单状态和库存。
4. 实物实际交给快递后，核对确认框中的公司、单号和数量，点击“确认交接出库”。
5. 订单变为“已发货”，结束该单库存预留，生成一次出库流水和一次交接事件。

交接后的快递信息只读。人工完成订单仍在订单页操作，文案明确不代表快递签收回执。自动揽收、轨迹订阅、签收回调、电子面单、一单多包裹属于后续阶段。

## 数据与兼容

- 新增 `order_shipments` 表，订单表结构和原状态枚举不变。`in_delivery` 在页面展示为“已发货”。
- 后端启动的 `Base.metadata.create_all` 会创建新表；已有记录不会自动生成虚构运单或交接时间。
- 已发货/已完成但缺少快递信息的历史订单可补录一次，备注必须说明来源。补录不重新出库；没有可靠交接时间时保持未知。
- 公司与运单号组合唯一，一期不支持多订单共用同一运单；录错可在交接前编辑，交接后不能直接覆盖。
- 运单仅校验基础格式，不宣称快递公司已经验证其真实有效性。
- 修改运单使用版本检查；同内容保存重试不重复写事件。交接使用幂等键和版本检查，旧版本不允许出库。
- 所有写入先锁订单。交接的运单、订单状态、预留、库存流水和时间线在一个事务中提交，失败时一起回滚。
- 原订单状态接口和原配送状态接口不再允许直接设置 `in_delivery`；应改用专用交接接口，避免绕过运单核对。

## 接口

- `GET /api/shipping/workbench`：状态、关键词、页码、每页数量；搜索订单号、收件人、手机号、运单号。汇总保留搜索条件，不受当前标签分页影响；按可靠收款时间优先处理，未知时间排后。列表查询不调用高德。
- `PUT /api/shipping/orders/{id}/shipment`：`carrier_name`、`tracking_number`、`remark`、`expected_revision`。首次版本填 0，后续用最新版本。
- `POST /api/shipping/orders/{id}/dispatch`：`expected_revision`、`idempotency_key`。返回含快递信息的完整订单。
- `GET /api/orders/{id}` 与订单列表增加可空的 `shipment` 字段。
- 原 `/api/shipping/map-settings`、`/api/shipping/orders/{id}/route` 等高德接口继续保留。

## 验证

前端 `npm test`、`npm run build`、`npm run format:check`。后端默认 SQLite 回归：`.venv\Scripts\python.exe -m unittest discover -s tests`。设置 `RUN_MYSQL_TESTS=1` 可运行隔离 MySQL 并发测试，它只创建/清理随机命名的测试数据库。

浏览器验收脚本为 `.local-test/shipping-phase1-acceptance.mjs`，使用独立 SQLite 测试库验证无坐标运单登记、真实高德路线、交接出库、订单双向跳转及手机布局，不写入应用业务数据。
