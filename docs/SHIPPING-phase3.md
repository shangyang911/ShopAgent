# 电子面单、批量发货、多包裹与实际运费

本期在现有发货工作台 `/shipping` 上扩展 Vue 页面和 FastAPI 业务，不替换高德地图、物流查询或库存事务。

## 业务规则

- 原 `order_shipments` 保留为一号包裹；额外包裹进入 `shipping_extra_parcels`。单包裹老订单无需改写。每单最多 100 个包裹。
- 待发货订单先登记一号包裹，再按需要登记附加包裹。附加包裹可使用不同快递公司；每个包裹有独立运单、备注、电子面单和实际运费。
- 任一包裹增改、移除都递增原运单 `revision`，它现在代表整单包裹清单版本。旧页面不能按过期清单交接。
- 同一快递编码和运单号不允许跨订单、跨包裹重复；快递别名及运单字母大小写统一核对。`shipping_waybill_identities` 的唯一键处理并发竞争，并同步检查升级前的原始运单记录。
- **整单的全部包裹统一交接、一次出库**。未实现按商品拆分后分批出库；包裹不独立推进订单完成状态。原交接事务只结束一次库存预留，时间线保存全部包裹的交接快照。
- 原有物流轨迹和异常跟进仍查询一号包裹。附加包裹可登记、打印和结算，本期不扩大轨迹轮询到附加包裹，也不推测其签收状态。
- 老订单补录一号包裹的来源备注规则保留；本期不为历史已交接订单新增包裹，不再次扣库存。

## 电子面单配置

适配快递100官方 [电子面单 V2](https://api.kuaidi100.com/document/dianzimiandanV2)，使用 `IMAGE` 获取网点图片面单；每个本地包裹独立申请一个单号。签名、月结账号和发件人资料仅存在后端。接口使用固定地址，关闭重定向。

在 `backend/.env` 设置下列内容后重启服务；这是独立于原物流查询账号的授权。

```dotenv
KD100_LABEL_KEY=企业授权码
KD100_LABEL_SECRET=企业密钥
KD100_LABEL_SENDER={"name":"真实寄件人","mobile":"真实联系电话","printAddr":"真实完整仓库地址"}
KD100_LABEL_ACCOUNTS={"shunfeng":{"partnerId":"真实月结账号","partnerKey":"网点密码","tempId":"真实面单模板ID","payType":"MONTHLY"}}
```

账号按快递编码配置，支持网点提供的 `partnerSecret`、`partnerName`、`net`、`code`、`checkMan`、`tbNet`、`expType` 等字段。具体必填项依快递公司的开通要求确定。缺少授权、寄件人、账号或模板时返回 503，不发请求、不生成虚构单号。配置接口只返回可用性和快递编码，不返回凭证或寄件人资料。

单个订单在“包裹与实际运费”申请面单；没有运单时申请一号包裹，已有主包裹时可申请新的附加包裹。已登记运单不能通过再次取号覆盖。取号只登记运单，不触发库存出库。

申请任务在外部调用前持久化。相同提交键与内容返回原任务；相同键更换内容返回 409。平台侧传稳定 `orderId` 和 `reorder=false` 作为额外防重措施。明确拒绝可在修正配置后新建请求；超时、不完整响应或取号成功但本地冲突会保留“结果待核实”，不自动再次取号。

有申请中或待核实的任务时，禁止本单运单修改、取消、退款和交接。进入包裹面板，在平台后台核对后填写取号结果及依据；已取号补录真实单号和官方面单链接，确认未取号则解除保护。服务中断遗留的申请中任务需等待至少 120 秒后核实。所有核实均追加审计事件。

打开面单链接不表示打印成功。批量打印接口先校验当前订单状态、清单版本及每一个包裹的面单，再记录“申请打印”事件。图片全部加载前不允许打印，避免漏打；默认排版为 100 × 150 mm，每张面单一页，需核对实际纸张和模板。平台图片异步生成、链接过期或第三方平台返回 PDF 时提示打开原链接核对，不伪装成批量打印成功。不会调用云打印机。取消订单不会自动取消快递平台取号任务，若需作废需在平台处理。

## 批量操作

勾选本页待发货订单并点击“核对选中订单”，可查看每单商品数量及全部包裹。没有运单的订单可选择快递和每包重量后批量申请面单；各订单使用独立稳定的请求键，逐单显示取号结果。不同重量请分组操作或进入详情逐单申请。

全部选中包裹都有电子面单后可打开批量打印页。人工登记的包裹不能凭单号伪造电子面单，混合批次需按已有纸质面单办理。

所有订单有有效运单且没有未决面单任务时，可确认全部实物已交接并批量出库。后端逐单事务处理，某一单失败不撤销已成功订单；响应逐单列出结果。批次键绑定完整订单和版本列表，重试已成功订单返回原结果，不重复出库。修改选单或运单版本视为新的操作。

## 运费口径

- `orders.shipping_fee` 仍表示向客户收取的运费，参与订单应收总额。
- `shipping_freight_records.actual_cost` 表示包裹实际结算支出。仅已交接或历史已发货包裹可以登记，金额保留两位小数，允许有来源依据的零元。
- 未登记是未知，不等于零。页面始终显示已登记合计及待结算包裹数量，不在不完整数据上给出最终运费利润。
- 每次登记需结算来源或修订说明；版本号防覆盖，同内容重试不重复记事件，修订保留前后值及操作人。
- 统计按交接时间筛选，前端日期按北京时间转换为左闭右开区间，并包含截止日。没有可靠交接时间的历史单仅计入不限定日期的汇总。
- 实际成本按包裹累加，客户运费按涉及的订单计一次。筛选某快递时，客户运费仍是匹配包裹所属整单的收入，不能理解成分摊给该快递的收入。退款后已产生的物流支出仍保留。
- CSV 按包裹导出全部匹配明细，未知金额留空，零元明确写 `0.00`，标识结算状态并处理公式注入前缀。

## API 与数据升级

所有接口沿用管理员 Cookie 鉴权：

- `GET /api/shipping/orders/{id}/packages`：全部包裹、整单版本、结算汇总及面单任务。
- `PUT /api/shipping/orders/{id}/packages/{no}`、`DELETE` 同路径：维护 2—100 号未发货包裹。
- `POST /api/shipping/orders/{id}/packages/{no}/label`：幂等申请面单。
- `POST /api/shipping/orders/{id}/label-tasks/{task_id}/resolve`：有依据地核实未决取号。
- `GET /api/shipping/label-settings`：不含凭证的配置状态。
- `POST /api/shipping/labels/print-batch`：校验面单批次、记录打印意图并返回官方图片链接。
- `POST /api/shipping/dispatch-batch`：逐单幂等交接，返回成功/失败明细。
- `PUT /api/shipping/orders/{id}/packages/{no}/freight`：登记或修订实际运费。
- `GET /api/shipping/freight-report`、`GET /api/shipping/freight-report/export`：汇总及 CSV，支持带时区的 `start_at`、`end_at` 和 `carrier`。

服务启动时 `Base.metadata.create_all` 增量创建五张表：`shipping_extra_parcels`、`shipping_waybill_identities`、`shipping_freight_records`、`shipping_label_tasks`、`shipping_dispatch_batches`。不改旧表、不回填库存、不猜历史运费。原订单 `.shipment` 响应保留主包裹以兼容旧页面；完整清单使用新增 packages API。

## 验证

后端：在 backend 执行 `.venv/Scripts/python.exe -m unittest discover -s tests -v`；设置 `RUN_MYSQL_TESTS=1` 可额外执行真实 MySQL 并发测试，测试仅使用随机创建并清理的隔离库。

前端：在 frontend 执行 `npm test` 和 `npm run build`。覆盖版本冲突、未知/零元运费、结算修订、别名重复运单、批量部分失败重试、面单幂等和待核实保护、批量打印前全量校验、未加载图片禁止打印。

`.local-test/run-shipping-phase3.py` 与 `.local-test/shipping-phase3-acceptance.mjs` 是本地隔离浏览器验收工具，使用 SQLite、8003/5176 端口，验证人工运单、多包裹、批量出库、运费登记、CSV 和手机布局，不访问真实取号接口。真实账号和打印机实物联调尚未进行。

2026-10-29 验证结果：后端 130 项测试通过（含 MySQL 隔离库并发测试），前端 87 项测试通过，类型检查、生产构建与变更文件格式检查通过。浏览器实际操作完成两单三个包裹批量交接、5.20 元与 0.00 元分别结算、一个未结算包裹仍明确显示、CSV 下载及 390px 手机布局检查，页面脚本错误为零。
